Retritis

Palliative treatments for agent-assisted development. A suite of Claude-Code plugins that turn your code, git history, build output, and policies into queryable SQL, so an agent can observe → understand → act → learn instead of grepping blind. This page describes how the pieces fit together as built — and how they should fit.

The ideas behind it

The mechanics below are downstream of a few convictions. Stated plainly:

Thesis

Agent-assisted development has chronic aches — context bloat, blind tool use, no memory between sessions, easy-to-miss guardrails. Retritis isn't a cure; it's a set of palliatives. The unifying move: turn everything an agent must reason about — code, git, logs, docs, and what it's allowed to do — into queryable data over two shared substrates, so tools compose by data, not by orchestration.

1 · Two substrates, composition by join

The keystone. DuckDB = facts (what is: ASTs, history, build output). SQLite = policy (what's allowed). Every tool reads/writes one of these. No tool calls another's API — they meet in shared tables and compose with a SQL join. Integration becomes emergent instead of hand-wired.

2 · Structured beats textual

Agents drown in raw text — a grep dump is tokens without shape. Hand them compact, ranked, queryable structure (AST nodes, commit rows, parsed errors) and the same answer costs 73–99% fewer tokens and is more correct (real call-graph edges, not string matches).

3 · Determinism where it suffices; inference only where it's needed

Coaching and interception are rules, not an LLM (kibitzer decides without a model in the loop — cheap, fast, predictable). Reserve inference for the genuinely fuzzy step — intent→program — and do it with a small local model (lackpy), not a frontier API. Spend compute proportional to the actual ambiguity.

4 · Capability as declarative data

What an agent may see, edit, call, and trigger is a cascading, CSS-like policy (umwelt) compiled to the shared SQLite store — not config scattered across tools. One source of truth, many consumers.

5 · The value is the loop, not any one tool

observe → understand → act → learn. Each tool is a station; the payoff is the cycle closing — a fix this session becomes a suggestion the next (agent-riggs: cross-session memory, trust scoring, pattern promotion). The system should get better the more it's used.

6 · Local-first, small, composable

In-process DuckDB, local models, no heavyweight infra. Each tool is single-purpose and composes through the substrate — so the suite is a toolkit you assemble, not a monolith you adopt.

The bet

As models get more capable, the bottleneck moves from "can it do the task" to "does the agent have the right context, guardrails, and memory." Retritis bets that a shared-substrate, structured, policy-governed, self-improving toolchain is how an agent becomes a reliable collaborator rather than an impressive-but-erratic one. Honest caveat: the wiring has largely caught up to the ideas — all eight plugins are packaged, the suites are green, and the loop has run for real (see Status) — but the closed learn-loop and persistent doc-context remain aspirational. The principles are settled; the plumbing is ~80% there.

Two substrates

The trick that makes composition emergent: there are only two shared stores. Everything reads/writes one of them, so tools join each other's data without coordinating.

DuckDB — facts

AST structure (sitting_duck) + git history (duck_tails) + build/test logs (duck_hunt, blq) + cross-file macros (fledgling) + session traces (agent-riggs) — all land in one DB.

→ "show me every caller of validate_token that changed since the failing build" is one query.

SQLite — policy

umwelt compiles your CSS-like .umw world files into a resolved-properties table. kibitzer, lackpy, and the sandbox builders all read the same PolicyEngine.

→ "can this agent edit src/auth/** and call git push?" is one lookup.

The loop (how it should run)

1 · Observe — blq captures the failure

Instead of pasting terminal output into chat, the build runs through blq; the failure becomes rows.

blq (MCP)
agent▸ blq.errors(run="latest")
test/auth/test_token.py:42  AssertionError  validate_token() returned None
src/auth/token.py:18        TypeError       expected str, got NoneType

2 · Understand — squackit/fledgling resolve context

Query the DuckDB facts: the definition, its callers, what changed recently.

squackit (MCP)
agent▸ squackit.find(".fn#validate_token", with="callers")
src/auth/token.py:18  def validate_token(raw)        # 3 callers
↳ login_flow() · refresh() · middleware.authenticate()
agent▸ fledgling.recent_changes("src/auth/token.py")
abc123  "refactor: drop default arg"  2h ago  ← suspicious

3 · Decide — kibitzer checks policy, suggests better moves

The agent reaches for raw grep; kibitzer intercepts, checks umwelt policy, offers the structured tool.

kibitzer (PreToolUse hook)
agent▸ Bash: grep -rn validate_token src/
⚠ kibitzer: use squackit.find(".call#validate_token") — structured, ranked, cached.
⚠ umwelt: edits to src/auth/** require review mode (policy: auth-guarded).

4 · Act — pluckit mutates, lackpy composes, jetsam ships

Either a direct pluckit chain, or describe intent and let lackpy generate a policy-checked, sandboxed program.

pluckit / lackpy / jetsam
agent▸ pluckit select('.fn#validate_token').addParam('raw: str').test().save('fix: restore type')
# or, from natural language:
agent▸ lackpy "restore the str type on validate_token and run its tests"
↳ generated: select('.fn#validate_token')...  [policy ✓, sandbox ✓]  → 3 tests pass
agent▸ jetsam.ship(msg="fix: validate_token type regression")

5 · Learn — agent-riggs records the pattern

The trace is scored and stored. Next time a similar failure appears, kibitzer/lackpy surface this fix first.

agent-riggs
agent▸ agent-riggs.record(trace)
pattern: "type regression after default-arg drop" → fix template stored (trust 0.0→seed)
ratchet candidate: promote to kibitzer suggestion after 2 more confirmations
Run for real

This isn't only a diagram anymore. In one session, observe → understand → act ran end-to-end on the suite itself: blq captured 105 structured test errors in fledgling, squackit/fledgling localized them to 3 root causes (a pluckit module rename, a ToolInfo API change, a git-path bug), the fixes landed, and a blq re-run reported 0 errors / 860 passing. The learn step (agent-riggs promotion) is still the open end of the loop.

Use cases

Goal: a test fails in CI and you want the agent to fix it without thrashing.

  1. blq turns the failure into structured rows (file, line, error).
  2. squackit/fledgling resolve the definition + callers + the suspicious recent commit.
  3. pluckit applies the minimal fix; jetsam commits with a real message.
  4. agent-riggs remembers the shape so the next regression is one suggestion away.

Goal: rename/restructure across a codebase without missing callers.

  1. squackit .find(".call#oldName") — every reference, ranked, no grep misses.
  2. pluckit chain: select(...).rename(...).callers().test() — mutation + verification in one breath.
  3. umwelt policy keeps the agent out of paths it shouldn't touch; nsjail runs generated code isolated.

Goal: get an agent productive in an unfamiliar repo fast.

  1. fledgling project_overview + doc indexing → the lay of the land.
  2. duck_tails surfaces who-changed-what; agent-riggs replays prior session context (via ffs on crashes).
  3. squackit compound workflows: explore / investigate bundle the common first moves.

Goal: let an agent act, but only within bounds you declare.

  1. Write a .umw world: which paths are read/edit, which tools are callable, resource limits.
  2. umwelt compiles it to the SQLite policy substrate.
  3. kibitzer enforces in-session; lackpy validates generated programs against it; nsjail caps the blast radius.

Honest verdict

Excellent bones; integration was the gap — and the gap has mostly closed. The two-substrate, compose-by-SQL design is genuinely elegant, and the value is measured — 73–99% less context than grep — not asserted. Going in it was "a pile of great tools," not a system: nearly everything broken was wiring (uninstalled marketplace, three PATH bugs, dormant search, unpackaged coaching, version drift), not code. That's now done — all eight plugins packaged, a full GPU host, green suites, real releases, and the loop run end-to-end on the suite itself. What remains is the harder last stretch: closing the observe→learn loop (agent-riggs promotion) and the persistent-index story. Net — a proven toolkit roughly 80% of the way to the cohesive system the catalog describes.
