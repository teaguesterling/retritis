## The two cases

  - **Case 2, coverage gap:** the agent loaded the tool, but the tool has no
    verb for the step. Measured: 7,504 raw ops in the snape corpus ran after
    jetsam was already in use, for operations jetsam does not cover.
  - **Case 3, the tool did not deliver:** the tool has the verb, but it
    failed, returned less than Bash, or could not reach the target. A
    transcript cannot tell this apart from habit. The evidence comes from the
    dispatch tests, where every subagent reported why it left a tool.

Under the dispatch rule, every case-3 failure now shows up as a reported
departure. Read those reports before you add a feature: they are the queue.

## Not filed: jetsam's read-only coverage (case 2)

These are the operations agents ran through raw `git`/`gh` **after** jetsam
was already in use. Counts are from all 971 snape transcript files.

| Op | Count | Op | Count |
|---|---|---|---|
| `git show` | 1,078 | `gh issue view` | 179 |
| `gh run view` | 831 | `gh issue create` | 130 |
| `gh run list` | 495 | `gh issue comment` | 115 |
| `git grep` | 385 | `git ls-remote` | 111 |
| `git rev-parse` | 250 | `gh api` | 109 |
| `git worktree` | 226 | `git ls-tree` | 93 |

Most of these are reads. One option is a read-only passthrough that the skill
approves outright, which needs no new verb per command. The other is verbs for
the top few: `show`, `checks` for any run, and `issue view`. Which one is right
is open. The "covered" set behind these counts is a judgment of jetsam's verbs,
encoded in `JETSAM_COVERED` in `bypass_buckets.py`.
